# 0.4.1 — objective solution and task controls

The objective column is the complete solving surface. It shows the current task, its progress, a wide focus block with every setting a suggestion can write, `solve` and `revert`, a short explanation, and prominent `new task` and `reset GUI` actions. The full settings panel remains available but is not needed to solve an objective.

## task lifecycle

A task is a scene, an active pigment and a hold target. The task row sits directly below the objective header, so its two actions stay visible even when the rest of the column is folded.

- `new task` selects a different scene, one of the three pigments and a target from 10, 20, 30 or 60 seconds. It restores the scene's rule defaults and the default brush, unpauses, regenerates the map, restarts the attempt and writes the task to the URL.
- `reset GUI` keeps the current scene and restores every setting from the scene baseline: scene rules, R pigment, 20 s target, brush 1 and unpaused. It regenerates the map, restarts the attempt and removes all GUI overrides from the URL.
- `new attempt` remains in the footer for a light retry: it clears hold progress and history while keeping the map, task and settings.
- Both task actions clear the active solution, changed-control highlights and stale explanation. The explanation panel then names the current scene, pigment and target and says that the settings are back at the scene defaults. The revert button is hidden because there is no undo point.

`Task.defaults` uses `UrlSettings.baseline(scene)`, so the application defaults and the selected scene profile have one owner. A shared URL restores the generated scene, pigment and target but not the random roll itself.

## layout

The objective column is 360 px wide and does not shrink below its two-column focus grid. Each column uses `minmax(0, 1fr)`, and labels, selects and sliders can shrink inside their rows instead of pushing the column wider. The reaction-mode select still spans both columns. The wider column gives every focus slider a usable track and leaves room for its value and absorb-direction button.

## suggestion

The plan is built from the live attempt, so it answers the state the player is in rather than a fixed script. Values are applied in this order; an edit is recorded only when the current value differs from the target.

| setting | target | why |
|---|---|---|
| cell production rate | 16 /f | growth is the strongest measured lever on ring share |
| production rule | low pigment | feeds every cell that already holds 5 % of the paint, not only cells already dominated |
| mix rate, the two rival pairs | 55 % | opens the pair so the reaction can run inside contested cells |
| reaction rate, the two rival pairs | 12 % | removes the rival share of a shared cell without clearing the ring |
| reaction direction, the two rival pairs | player consumes rival | absorb is one-way, so the direction decides who wins the cell |
| reaction mode | absorb | converts the rival share into your own gas, no mass burned |
| dilution exponent | 1 | keeps weak traces reacting, so a thin front still flips |
| brush | 2 | only when the ring holds less than one unit of the active pigment; painting is the remaining move |

Higher existing values are kept (`max`), so a hand-tuned setup is not flattened. Directions are always written, because absorb without the right direction helps the rival.

A focus pair-rate row owns both its value and its enabled bit. The suggestion enables both rival pairs even when their target rates are already stored but the pair switches are off. Such an edit is described as `enabled` in the explanation and as `off → value` on the slider; the main pair checkbox and the focus row are both highlighted.

States with nothing to do return an empty plan: the objective is already held, or the suggested setup is already in place. A ring without the player's pigment still gets the rules, plus a note to paint inside the ring, because both growth and absorb need the paint present.

## apply, follow and revert

- `Solution.apply` reads `Settings`, returns the plan (headline, notes, edits) and records the original values and pair masks once. Repeated solves and pigment switches keep a single undo point.
- `Solution.revert` restores the recorded values and pair masks and returns a plan with reversed edits, so the same highlight works for the undo.
- `Solution.clear` drops the undo point when a task action replaces the settings wholesale.
- Switching pigment re-applies the suggestion: the rival pairs and the absorb directions follow the new paint, and the explanation panel updates.
- Switching scene replaces every rule, so the undo point restarts from the new scene and the suggestion is applied on top of it.

## GUI

- Focus block rows: cell production rate, production rule, pressure speed, viscosity, brush, dilution exponent, mixing and reaction rate against each rival with a direction button, and the reaction mode. This is the exact set a suggestion may write; `solution-checks` fails if the two lists drift apart. Pair switches are reached through the pair-rate rows, which auto-enable the pair.
- `solve` and `revert` sit under the focus grid. `revert` appears only while a suggestion is active.
- Explanation panel under the buttons: a headline (`take the ring`, `keep the ring`, `objective held`, `suggested setup already in place`, `reverted`, `new task`, `GUI defaults`), short notes about the settings or the current task, and a compact list of the settings the click changed.
- Highlight: every changed row gets an amber outline, a pulse, and its value display shows `old → new` for 2.6 s; pair checkboxes, direction buttons and the reaction-mode button are marked the same way. The changed list in the explanation panel stays after the pulse fades.

## measurement

`experiments/objective-bench.js` has a `solution` axis: the same opening claim as every other axis, base run versus a patch applied at frame 60, 160 frames, six scenes, fixed-key lines. The spread of that axis is the gain the button buys.

`node experiments/objective-bench.js 160 solution`:

	axis=solution scenes=6 mean_hold_spread_s=0.7 mean_control_spread_s=0.8 mean_share_spread_pp=26.4 sensitive=1

Scenes 0, 4 and 5 open above the 55 % requirement and stay there (no change). Scenes 1, 2 and 3 move from no control to 1.4–1.7 s of control and from 34–55 % to 100 % peak ring share. No scene loses control time.

`solution-checks.js` holds the contract: own pairs only, absorb direction per pigment, mode and dilution, production raised but higher values kept, disabled pairs enabled at their target rates, exact revert of values and masks, no-op for held objective and for an already suggested setup, brush and paint note for an empty ring, focus-block coverage of every writable key, and a 24×24 arena where the patch flips contested ring cells to the player (0 → 113 of 113 cells) while the unpatched run flips none.

## validation

- L2: `npm run checks` (simulation, concentration, objective, solution), `npm run smoke` (jsdom: solve applies, marks rows, writes the URL, explains, reverts, follows a scene change, reverts to the scene rules, generates a task, restores GUI defaults).
- Manual pass: boot, read the task row, press solve while below the requirement and watch the ring share climb; read the changed list and the highlighted rows; press solve again (no-op); switch pigment and check the absorb directions follow; switch scene and check the suggestion stays applied and the undo restores that scene's rules; press revert and confirm every marked value returns; press new task and check a different scene, pigment/target and clean defaults; press reset GUI and check the current scene returns to its baseline with every override removed.
